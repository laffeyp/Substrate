# Substrate — Vocabulary v0.2 Rationale (RATIFIED)

*The first evolution of the founding vocabulary. Companion to `0.2.json` (the vocabulary), `0.1.json` (the retained locked-v0.1 audit trail — NOT deleted, per the no-deletions discipline), `0.1-rationale.md` (the founding rationale), and `proposals.json` (proposal ledger). This document records what v0.2 changed relative to v0.1 and why, per the supervised-grammar-evolution taxonomy (`sdd-kit-2/grammar/PRINCIPLES.md`).*

**Status:** RATIFIED 2026-06-13 by Architect ruling (Ruling 1). `0.2.json` has `locked:true`, `prior_version:"0.1"`. Validator-extras posture: **strict** (unchanged — bus-boundary validation is mandatory and non-configurable, product principle 4).

---

## Why v0.2 exists

v0.1 locked the founding vocabulary at the Sprint-0 Vocabulary Session. During Waves 5–6 the implementation needed three additions to the **`substrate.TriggerFired`** payload that v0.1 did not catalogue. Under strict validator-extras, an uncatalogued field is a contract violation, so these were carried *implemented-ahead-of-ratification* as typed proposals (the exact mechanism the eight-proposal taxonomy exists for) and surfaced for an Architect ruling rather than silently emitted. Ruling 1 ratifies all three and bumps the vocabulary. **v0.2 is purely additive: it changes exactly one tag's payload and the top-level metadata; all 38 entities, the other 11 lifecycle tags, and every Layer 3–10 section are byte-identical to v0.1** (verified by diff). No tag was removed; no semantics of an existing field changed.

This is the founding vocabulary's first evolution, and it is the intended path: a need surfaced during implementation → typed proposal → Architect ratification → additive version bump with a rationale entry → the new version becomes the contract. The prior version is preserved as the audit trail so a future session can argue back against *why* the shape changed.

## The three ratified changes (all on `substrate.TriggerFired`)

### 1. `instance: str` (required) — `P-TRIGGERFIRED-INSTANCE` — `PAYLOAD_FIELD_PROPOSED`

The ULID instance_id of the Producer the firing schedules.

**Why.** It closes **provenance closure** (F-OBS-2 / F-OBS-3) and conformance **check 11**: `explain_producer` / `trace_ancestry` (tech §14, Wave 6) must link a `substrate.ProducerStarted` back to the *exact* firing that scheduled it. `ProducerStarted` carries the subject Producer's `{kind,instance,parent}` (ratified into v0.1 as `P-SUBJECT-ID`), but without `instance` on `TriggerFired` the firing→Producer link had to be re-derived from the resolved-input hash, which is neither unique nor reliable. With it, the spawn link is direct and the provenance graph is acyclic and rooted at `RunStarted` by construction. This is the exact symmetry of the v0.1 `P-SUBJECT-ID` ratification, one altitude up (the firing decision rather than the started Producer).

**Source.** product F-OBS-2 / §7 check 11; tech §14 (`explain_producer`, `trace_ancestry`); the P-SUBJECT-ID precedent in v0.1.

### 2. `factory: str` (required) — `P-TRIGGERFIRED-FACTORY` — `INVARIANT_PROPOSED → ratified as a payload field`

The Producer KIND the firing schedules (the trigger's `starts`; the initial kind for an initial Producer).

**Why.** It reconciles a kernel-vs-tech drift v0.1 had explicitly deferred: kernel v15's lifecycle table names `factory` among `TriggerFired`'s identified elements, while tech §6.2 step 5 omits it (the spawned kind is *recoverable* via the manifest's `triggers[].starts`, arguing it is redundant). Carrying it on the frame is the cheapest read of the spawned kind for a reader/inspector and removes the need to join against the manifest for the common provenance query. For an initial Producer (which fires under `trigger_id:"__initial__"` with no manifest trigger entry), `factory` is the only on-frame record of the kind. Ratifying it onto the frame settles the drift in favor of the kernel's enumeration.

**Source.** kernel v15 lifecycle table; tech §6.2 step 5; the v0.1 deferral note on the `substrate.TriggerFired` tag.

### 3. Rename `$blob` → `input_blob` — `P-TRIGGERFIRED-INPUT-BLOB` — `PAYLOAD_FIELD_PROPOSED`

The oversized-resolved-input field (carrying a BlobRef), mutually exclusive with `resolved_input` (D-5: exactly one present).

**Why.** v0.1 named this field literally `$blob`, of type `BlobRef`. But a `BlobRef` *serializes to* `{"$blob":"sha256:<hex>","bytes":n}` — so a field literally named `$blob` produced the on-disk shape `{"$blob": {"$blob": ..., "bytes": ...}}`, where the field key and the BlobRef's own discriminator key are textually identical. That is a genuine reader/CLI-author footgun (which `$blob` is "the field" vs "the ref"?). The emission-payload blob case has no such collision (there the payload genuinely *is* a bare BlobRef — the whitelist payload type). Renaming the **TriggerFired** field to `input_blob` de-overloads the sentinel while keeping the BlobRef value shape and the D-5 mutual-exclusivity with `resolved_input` intact. `input_sha256` (the citable identity) is unchanged and always present.

**Source.** D-5; tech §3.7 / §6.2 step 5; the Wave-6 review finding that localized the `{"$blob":{"$blob":..}}` collision.

## What did NOT change

- **No new tags, no removed tags.** The 12 `substrate.*` lifecycle kinds are exactly v0.1's.
- **No semantics of an existing field changed** (the rename keeps the same value shape and requiredness; the two additions are new required fields the runtime already emitted ahead of ratification).
- **Validator-extras stays strict.** The additions are now *catalogued*, so frames the runtime already emits become conformant; the strict posture is unchanged.
- **Wire schema versions (`<kind>@N`) are untouched.** The vocabulary version (0.1→0.2) is a distinct axis from the per-kind envelope schema version; `substrate.TriggerFired@1` remains `@1` (v0.2 formally declares its fuller payload). The record now also self-describes the vocabulary version it was written against in `RunStarted.config.vocab_version` (newly recorded, "0.2") so replay/inspection can key on it.

## The D-8 equivalence relation — exclusion set made explicit (v0.2)

v0.2 also pins, for the record, the exact **supplementary-metadata exclusion set** used by `first_divergence` / D-8 (tech §14, product §D-8). D-8 is "ordered equality of (event-kind sequence, **decision-identity** sequence, canonical payload hashes), supplementary metadata excluded" — but the spec only named `t`/host/config; the implementation must enumerate the rest, and the exclusion is part of what makes the equivalence relation *honest* (two runs of the same deterministic topology must be equivalent). Excluded from the per-frame comparison hash, on `substrate.*` lifecycle frames only:

- **`run_id`, `instance`** — fresh ULIDs / the run id (per-run identity, not decision content).
- **`producer.instance`, `producer.parent`** — the subject ref's run-specific ULIDs. `producer.kind` is KEPT (it is decision identity).
- **`measured_us`** (on `substrate.PredicateQuarantined`, budget path) — wall-clock microseconds of a predicate call; a timing MEASUREMENT, not identity. (Without excluding it, two runs that both budget-quarantine the same predicate would spuriously diverge — a false conformance-check-13 positive.)
- **`error`** (on InputBuildFailed / ProducerFailed / RunFinalised{kernel_error} / PredicateQuarantined{exception}) — a `repr(exc)` that can embed temp paths or object addresses; normalized to a stable sentinel for the comparison. The frame KIND already carries "a failure of this class happened here"; the repr text is supplementary.

KEPT (decision identity): `input_sha256`, `firing_key`, `reason`, `trigger_id`/`route_id`, `policy`/`decision`, `k` (a config constant), `view`/`seq` (real positions), and the entire payload of any **application** (non-`substrate.*`) frame — application content IS the decision being compared and is never normalized. This exclusion set is also written as an additive technical-spec amendment note (see the product/technical amendment cut alongside Ruling 2).

## Open / deferred (carried forward from v0.1, unchanged by this bump)

The v0.1 open items remain open and are unaffected: `P-SUBJECT-ID`/`P-INJECTION-FIELDS`/`P-INVALID-PRODUCER-FIELD` (ratified into v0.1), the `ENTITY_MERGE` proposals (ProducerId/ProducerRef; Run/RunRecord/RunResult), the kernel v16 reconciliation note, and the PredicateQuarantined discriminated-shape proposal. Replay Level 3(b) deferral is handled separately as a spec amendment (Ruling 2), not a vocabulary change.
