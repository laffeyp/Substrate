# Horizon: Substrate — Concurrent Streaming Dataflow Runtime
**Status: DRAFT v8**

---

## What this is

Substrate is a concurrent streaming-dataflow runtime. Producers consume typed inputs and emit typed events onto an append-only, totally-ordered, replayable bus. When a predicate over bus state holds, a Trigger fires, creating a new Producer with input built from current state. Producers may subscribe to bus Views, compute derived events, and route typed messages into future Producer inputs. Termination is policy-driven: typed events, Producer completion, failure, cancellation, and quiescence are interpreted by topology-specific rules.

This is an orchestration substrate for arbitrary streaming computations. Inputs are typed; outputs are streamed events and may be stochastic, deterministic, or a mix. The same primitives wire an LLM feeding a sentiment classifier feeding another LLM, two stochastic agents playing iterated prisoner's dilemma, a swarm of simulators feeding a synthesizer, a code-writing pipeline with live verification, or any other shape where typed-input streaming-output computations need to be wired together with concurrent execution, predicate-driven firing, and side-channel introspection.

Producers are not necessarily LLMs. An LLM call, a small ML model, a subprocess, a parser, a test runner, a search backend, a sensor, a deterministic transform, a simulator, a human input stream — all are Producers if they emit typed events. Conversation and refinement are application topologies, not substrate concepts.

---

## Why this is non-obvious

This is not a more complicated agent loop. It is a different execution model: concurrent streamed computation with predicate-triggered topology evolution.

The mainline LLM tools — Aider, Claude Code, Cursor, Cline — share one shape: one strong model, a set of tools, a tight synchronous request/response loop. The chat-multi-agent direction (AutoGen, CrewAI, MetaGPT) is the same shape with a turn-taking scheduler and prompt-defined "roles." Their primitives are model call and tool call with synchronous semantics. There is no buffer to predicate over, no overlap to exploit, no auxiliary producer running in parallel and injecting mid-stream.

LangGraph is closer kin. It introduces cycles and conditional edges over a shared state object, enabling graph topologies that the DAG-only approaches cannot express. But LangGraph executes one node at a time (a node runs to completion before the next fires), its state is a mutable global object rather than an append-only log, and its graph is declared statically before execution — Triggers cannot fire new nodes dynamically. Substrate is on a different axis from LangGraph, not further along the same one.

The substrate's departure is exactly here: N Producers run concurrently from the same bus, Triggers create new Producers dynamically as predicates are satisfied, and the bus is the single append-only record of everything — not a mutable state object, not a turn-taking transcript.

## Relation to prior work

The substrate draws on ideas from several distinct traditions. Understanding which it resembles and where it departs is the clearest way to locate what is actually new.

**Kahn Process Networks (KPNs)** (Kahn, 1974) are deterministic dataflow networks where processes communicate via blocking reads on FIFO channels. KPNs guarantee determinism: given a fixed input history, every process always produces the same output. Substrate departs from KPNs in two deliberate ways. First, determinism is not required — stochastic Producers (LLMs, randomised search) are first-class. Second, the communication model replaces point-to-point FIFO channels with a shared bus and predicate-driven subscriptions. A View over one Producer's events is a channel; but complex multi-source predicates — "fire when at least three Producers have emitted final answers" — require no extra machinery. KPNs would need explicit merge processes and coordination channels to express the same condition.

**Naiad / Timely Dataflow** (Murray et al., 2013) introduced logical timestamps and progress tracking to enable cyclic dataflow without global synchronization barriers. Naiad's central innovation — the notion of a computation frontier, a set of logical timestamps beyond which no more messages will arrive — is the mechanism that lets iterative computations know when an iteration is complete. Substrate's Triggers play a structurally similar role: a Trigger fires when a predicate is satisfied, giving downstream Producers a meaningful "go" signal. But Substrate achieves this through event predicates and firing policies rather than timestamp dominance and progress proofs. The key tradeoff: Naiad's progress tracking is formally verifiable and enables stronger guarantees about iteration termination; Substrate's predicate model is more expressive and compositional but requires the topology author to reason about predicate satisfaction conditions. Naiad also requires a static dataflow graph declared before execution; Substrate's Triggers can create new Producers dynamically, making the topology graph evolve at runtime. One more difference worth naming: Naiad's graph evolution is described as an implementation concern not well-supported by its model; Substrate makes topology evolution a first-class substrate feature, with TriggerFired events on the bus as the record of it.

**SEDA (Staged Event-Driven Architecture)** (Welsh et al., 2001) decomposes applications into pipeline stages connected by bounded queues, with adaptive thread pools per stage. SEDA Producers resemble Substrate Producers, and SEDA's queues resemble a per-stage bus. The key differences: SEDA stages have fixed wiring (static pipeline topology); Substrate stages are created dynamically by Triggers. SEDA focuses on load-conditioned concurrency and adaptive resource management; Substrate focuses on predicate-driven topology evolution. SEDA does not address recursive or dynamic topologies. Its design philosophy — isolate stage-to-stage coupling behind queues — is shared, but Substrate generalises it by making the bus the universal coupling point rather than per-pair queues.

**Temporal** provides durable, replayable workflow execution via event sourcing: the workflow's event history enables replay and recovery. Substrate's bus serves the same archival function. But Temporal's execution model is sequential — one workflow coroutine at a time, activities run one at a time per thread — whereas Substrate's execution model is concurrent: N Producers running simultaneously. Temporal's "signals" (pushing data into a running workflow) are analogous to Routes, except for a critical difference: Temporal signals are delivered into a *running* workflow's execution; Substrate Routes stage messages for *future* Producer instantiations, because running Producers have immutable input (see §The primitives: Producer). Temporal's replay is stronger than Substrate's Level 3 (see §Replay semantics) because Temporal requires deterministic activities; Substrate's replay honestly bounds what is and is not replicable for stochastic Producers.

**Reactive Streams / Rx** define Publisher, Subscriber, Subscription, and Processor with credit-based backpressure. Substrate's Producer resembles a Publisher; its Bus resembles a broadcast Subject. The critical difference: Reactive Streams wire point-to-point — one Publisher, one or many Subscribers — and backpressure flows back from Subscriber to Publisher over the subscription. Substrate routes everything through a shared bus with predicate-driven dispatch; there is no direct backpressure channel from a downstream consumer back to a specific upstream Producer. This is an honest tradeoff: Substrate gains compositional flexibility (any predicate over any View can trigger any Producer) at the cost of requiring the implementation to handle backpressure at the bus level rather than at the subscription level. Reactive Streams' backpressure protocol is the best available approach for the bus implementation to adopt.

**π-calculus** provides a formal model for processes communicating via named channels, where channel names are first-class values — enabling dynamic process creation and topology evolution. Substrate's Triggers play the role of π-calculus reduction rules: dynamic process creation gated on a communication event. The bus is analogous to a shared name space. Substrate is not a formal calculus — it does not have reduction semantics or bisimulation — but shares the process-calculus design ideology that computation topology should be able to evolve dynamically as a first-class behaviour, not as a bolted-on feature.

## Vocabulary discipline

The substrate's vocabulary is deliberately not anthropomorphic, and each term is chosen to carry the meaning of what it does rather than to label a concept.

- Producer, not speaker / actor / agent / participant / voice.
- Bus, not conversation / transcript.
- Predicate, not cue.
- Trigger, not spawn / handoff / activation. A Trigger is a thing that fires when a condition holds — the word means what it does.
- Topology, not cast.

Each exclusion prevents a class of misdesigns; the rationale is in §Non-goals.

Application topologies that happen to be conversations do not get a bespoke vocabulary. Two LLMs conversing are two Producers; the runtime does not introduce speaker or voice concepts to flatter the application.

---

## Non-goals

Things this substrate does not try to be, and the design problems each of those would have imported:

**Not an agent runtime.** No identity, lifecycle, planning, or goal state attached to Producers. Producers are functions that stream.

**Not a conversational orchestrator.** No turn-taking, politeness, conversational repair, or talking-past detection in the substrate. Those are application instruments wired as Producers.

**Not a chat framework.** Bus is not a transcript; events are typed and producer-tagged, not styled lines of dialogue.

**Not a YAML DSL for pipelines.** Topology is host-language code.

**Not opinionated about prompt construction.** A Producer's input is built by an application-layer function before the Producer starts; the substrate is not aware of prompts as a concept.

**Not a verification framework.** Checks are Producers that emit typed events; predicates may gate on those events. The substrate does not know what "verified" means.

**Not LLM-specific.** Producers may be LLMs, classical ML models, deterministic transforms, simulators, or anything else with a typed-input streaming-event-output shape. The substrate has no awareness of model providers, prompts, or tokenisation.

## The primitives

Eight.

### 1. Producer

Typed input → async stream of typed events. The runtime calls `start(input) → AsyncIterable[Event]` (or its back-pressure-aware equivalent) and consumes events until the Producer completes, fails, or is cancelled.

**Input immutability is a formal contract.** A Producer's input is sealed at instantiation time — when the Trigger's `input_builder` returns. No running Producer's input can be mutated by Routes, other Producers, or the runtime after `start()` is called. This is not a recommendation; it is the boundary that makes replay deterministic at Level 2 and makes Routes well-defined. Routes stage messages for future instantiations, never for running ones.

Producers are identified by a typed `ProducerId` with kind metadata, not free strings.

### 2. Event

Append-only typed record with `ProducerId`, kind tag, payload, and a bus sequence number (the event's logical position in the bus total order). A run-monotonic wall-clock timestamp accompanies each event as supplementary metadata but is not the event's identity. Events are the substrate's unit of currency. Both data-plane events (Producer output payloads) and control-plane events (Trigger firings, injection decisions, termination decisions; see §Lifecycle) live on the same bus.

Two timestamps are distinguished:

- **Bus sequence number**: monotonically incrementing integer assigned by the bus at serialization. Establishes total order. Used by predicates and Views for consistency.
- **Wall-clock timestamp**: the time the event was appended. Supplementary; not used for ordering.

Predicates and Views reason over sequence numbers, not wall-clock time, for consistency and replay correctness.

### 3. Bus

The append-only, **totally ordered** event log. Every event is assigned a bus sequence number at serialization time; no two events share a sequence number; no event's number may decrease. Concurrent Producers appending simultaneously are serialized at the bus — their events acquire distinct sequence numbers and a definite order. The total order is the foundation of consistent View computation and deterministic predicate evaluation.

Single-source-of-truth for the run. Predicates and Producers do not inspect the log directly; they inspect Views over it.

**Per-run is the default.** A persistent bus across runs is opt-in for cross-run pattern work (materialised history, mining for topology presets, longitudinal diagnostics). In the persistent opt-in, `ProducerId.instance_id` is unique only within a run; a run-id prefix is required for cross-run uniqueness.

### 4. View

A deterministic projection over the bus. Examples: "accumulated text payload from Producer P," "all events of kind K since sequence number N," "count of events matching predicate Q." A buffer — accumulated payloads from one Producer — is the most common View.

**Materialisation and consistency.** Views are materialised incrementally: each time an event is appended to the bus (acquiring its sequence number), all Views that subscribe to that event's kind or producer are updated. This update happens synchronously with the serialization — before any predicate is evaluated against that event. A predicate evaluated at sequence number N sees a View that reflects all events with sequence number ≤ N. This is the consistency guarantee: predicates never see partial state from concurrent appends.

Determinism of Views over the event log is the foundation of replay.

### 5. Predicate

A cheap deterministic gate over Views and events, expressed as a host-language callable. Predicates run on every relevant bus append, so they must be O(1) or near it. Expensive semantic checks are themselves Producers that emit typed events; predicates gate on those events.

**Evaluation protocol.** On each bus append (at sequence number N, with all Views updated to N), the runtime evaluates all registered predicates in an implementation-defined but stable order. A predicate that returns true causes its associated Trigger to fire. Predicate evaluation is synchronous with the append cycle; no predicate races another for the same bus snapshot.

The predicate taxonomy:

- **Event-local**: matches a single just-appended event ("this event has kind=DeclarationComplete").
- **Buffer-local**: a View of a single Producer's stream crosses a threshold ("Producer A's text buffer matches `/\.\s/`").
- **Bus-view**: a View over multiple Producers ("at least three candidates have emitted final answers").
- **Composite**: boolean combination of the above ("A emitted X AND B emitted Y AND no termination signal yet").
- **Externalised**: gates on a derived event emitted by an auxiliary Producer ("the scorer Producer emitted score > 0.8").

Predicates must not embed expensive computation. The runtime should reject or quarantine predicates that exceed a budget per call.

### 6. Trigger

The substrate's mechanism for creating Producers. A Trigger pairs a predicate with a Producer factory and a recipe for building that Producer's input. Its shape is `(predicate, producer_factory, firing_policy, input_builder)`.

When the predicate holds against current bus state, the Trigger fires. Firing means: the runtime calls `input_builder(bus_state)` to construct the new Producer's input from whatever it needs to read off the bus, calls `producer_factory(input)` to create a Producer task, and starts the task. Producers come into existence only through Triggers; everything in the run is driven by bus state crossing predicates.

A Trigger's predicate may match events from any Producer in the run, including Producers that earlier firings of this same Trigger created. Topology depth is therefore unbounded. Recursive decomposition (planner → solvers → sub-solvers → …), dynamic-programming patterns, and arbitrary recursive composition fall out directly. No per-depth Trigger registration is required.

Firing policies (how often a Trigger may fire while its predicate is satisfied):

- **Once**: first satisfaction fires; further satisfactions ignored.
- **PerEvent**: each event that newly satisfies the predicate fires the Trigger once.
- **PerKey**: keyed firing; one firing per distinct key value extracted from the matching event/View.
- **WhileTrue**: continuous; fire at every event while the predicate holds, with optional cooldown.

Trigger graphs are arbitrary: fan-out (one predicate fires many Producers), fan-in (a predicate requires multiple Views to satisfy), conditional (predicate inspects content to choose which factory to invoke). Each firing emits a TriggerFired control-plane event on the bus so that the topology's evolution is visible in the trace.

**Divergence.** A Trigger whose predicate is permanently satisfied by the events produced by its own firings will fire unboundedly. Infinite regress is not blocked by the substrate; it is the topology author's responsibility to constrain it using firing policies (Once), keyed deduplication (PerKey), or TerminationPolicy.

### 7. Route (Injection)

Rule for incorporating emitted typed events into the inputs of future Producer instantiations. A Route is `(source_predicate, target_input_slot, transform)`. Routes operate push by default: when source events satisfying the predicate are observed, the transform produces a typed message that the runtime stages for matching future Triggers; the Trigger's `input_builder` reads staged messages at firing time. A pull variant is also available for cases where lazy resolution matters: the `input_builder` may explicitly query a Route when assembling input.

**Route timing.** A Route's staged message becomes visible to the next Trigger firing that evaluates after the Route is applied. Because the bus is totally ordered, "next firing" is well-defined: it is the next Trigger evaluation in the append cycle following the cycle in which the route-triggering event arrived. Routes are never retroactively applied to already-started Producers; they only influence future instantiations.

### 8. TerminationPolicy

A host-language callback that interprets termination signals (Producer-emitted events of a designated kind), Producer completions, failures, cancellations, and quiescence (no runnable Producers, no satisfiable Triggers) into one of: `cancel-others`, `let-finish`, `finalise-run`, `continue`.

A termination signal is just an event; the policy is what makes it consequential.

**Scoping.** Per-run and per-Producer policies may coexist. When both apply, they are composed: per-Producer policies are evaluated first and may emit `cancel-others`, `let-finish`, or `continue` relative to the Producer's subtree; the per-run policy then interprets the aggregate of all per-Producer decisions plus the global run state. If a per-Producer policy emits `cancel-others` and the per-run policy emits `let-finish`, the per-run policy wins at run scope — the cancelled Producer's siblings continue. If the per-run policy emits `finalise-run`, it overrides all per-Producer policies.

**Cancellation propagation.** By default, cancellation is flat: cancelling a Producer does not automatically cancel Producers that were created by its Trigger firings. Subtree cancellation — cancel a Producer and all Producers transitively created by its events — is available as a named composition in the standard policy recipe book. The default being flat prevents surprising cascade cancellations in fan-out topologies where child Producers are logically independent of the cancelled parent.

The substrate ships a small recipe book of standard policies (`cancel-all-others`, `let-finish`, `quiescence-with-watchdog`, `threshold-count`, `all-completed`) as named functions, but the contract is the callback, not the recipe set.

## Lifecycle and control-plane events

Replayability requires the bus to record control decisions, not just data payloads. The runtime emits the following event kinds in addition to producer-defined payload kinds:

| Kind | Meaning |
|---|---|
| `TriggerFired` | A Trigger's predicate was satisfied and the Trigger fired; identifies trigger, factory, key, and resolved input. |
| `ProducerStarted` | Producer task began running. |
| `ProducerEvent` | Wrapper around a Producer's typed payload event. |
| `ProducerCompleted` | Producer's stream exhausted normally. |
| `ProducerFailed` | Producer errored; payload includes error. |
| `ProducerCancelled` | Runtime cancelled Producer per policy. |
| `InjectionApplied` | Route contributed typed messages to a Producer's input. |
| `TerminationMatched` | TerminationPolicy fired; identifies the policy decision. |
| `RunFinalised` | Run produced its final output. |

These are first-class bus events. Replay reconstructs not just outputs but the full topology evolution.

## Topology patterns

Side-channels, adjudicators, repair detectors, scorers, typecheckers, parsers, simulators, and human input streams are not primitives. They are topology patterns built from Producer + subscription View + Route. Two additional patterns are worth naming explicitly because they address commonly encountered runtime concerns.

**Retry.** Error recovery is a topology pattern, not a substrate primitive. A Trigger with predicate on `ProducerFailed` events and firing policy `PerKey` (keyed on the failed Producer's kind) fires a replacement Producer with the same input, optionally enriched via a Route that injects the failure reason. Retry limit is enforced by a predicate that counts retry attempts from the bus View. The substrate does not need to know what "retry" means; the topology expresses it.

**Progress gating.** A predicate over a Bus-view — "at least N candidates have emitted final-answer events" — fires correctly because the bus is totally ordered and Views are updated synchronously before predicate evaluation. There is no race between Producers to be "counted." If the topology requires waiting for all currently-running Producers of a given kind to complete before firing a downstream Producer, the predicate is "count of ProducerCompleted events for kind K equals count of ProducerStarted events for kind K." This is computable from the bus View without any additional coordination primitive.

## Replay semantics

Replay has three levels. Each is honestly bounded.

**Level 1 — Event replay.** Reconstruct all Views, displayed/output state, and any deterministic derivation from the recorded event log. Always possible for any recorded run.

**Level 2 — Schedule replay.** Reconstruct Trigger, injection, and termination decisions from recorded control-plane events. Always possible given Level 1, because the runtime's decisions are themselves recorded events. This is the substrate's primary replay guarantee: the topology's full execution history — which Triggers fired when, which Producers were created, which Routes applied, which policies triggered — is deterministically reconstructable from the bus.

**Level 3 — Deterministic re-execution.** Re-run the topology and get equivalent behaviour. Only possible if either (a) every Producer's output is reproducible (seeded deterministic Producers, recorded inputs and randomness), or (b) every Producer's emitted events are substituted from the recorded log instead of being recomputed. For stochastic Producers (LLMs, randomised search), Level 3 is achievable only via substitution.

The honest substrate claim: the event bus is replayable as an execution trace. Replay reconstructs Views, buffers, firing timing, injections, and terminations. It does not imply deterministic re-execution of stochastic Producers unless their emitted events are recorded or their randomness is controlled.

The trace/replay UI is not part of the substrate. It is a separate tool that reads the persisted event log. The substrate's responsibility ends at emitting the bus.

## Failure modes this substrate addresses

**Sequential bottlenecks in tight-loop architectures** (typecheck waits for full code; test waits for full typecheck) collapse, because each stage fires at the earliest predicate it can satisfy.

**"One strong model, no leverage from weaker models"** is expressible as an ensemble + adjudicator topology instead of being baked out of the architecture.

**"One prompt, one model, one shot" rigidity** gives way to multiple Producers contributing to one Bus over time.

**"All Producers must be the same kind of thing"** — collapsed by Producer being a Protocol that admits LLMs, ML models, deterministic transforms, simulators, and external processes equivalently.

**Recursive decomposition** (planners firing solvers firing solvers) is expressible directly via Triggers whose predicates match events at any depth.

**Static graph topology** (LangGraph's limitation, Naiad's deliberate constraint) is superseded: new Producers can be created at runtime as predicates are satisfied.

---

## Failure modes this substrate introduces

**Predicate authoring is a new design surface.** Bad predicates fire Triggers too early (downstream instantiates with insufficient upstream content) or too late (no overlap benefit). The predicate taxonomy is the first guard; progress gating patterns (see §Topology patterns) are the second.

**Backpressure between Producers that emit faster than the bus can process** is a real concern. LLM Producers are bounded by token rates; deterministic Producers (parsers, file watchers, simulators) will saturate without explicit backpressure on the bus. The implementation must address this; the substrate's design is compatible with credit-based backpressure from the Reactive Streams specification.

**Auxiliary-Producer cost is unbounded by default.** Each is an extra invocation; topologies that wire many of them can blow cost out. Firing policies (especially Once and PerKey) are the primary throttle.

**Debugging a topology with N Producers + K Routes + Trigger timing is harder than a synchronous chain.** Replay + the lifecycle event stream is the answer, but the UI for it is itself a design problem — and one that the substrate intentionally defers.

**"Replayable" cannot be oversold.** The Levels 1–3 distinction is the honest boundary. Stochastic Producers require recorded outputs to achieve Level 3. Building operational expectations around Level 3 for topologies with LLM Producers requires substitution infrastructure.

**LLM context is bound at instantiation time.** Routes inject into future instantiations, not running Producers. "Live" feeling interactions are chunked instantiations or kill-and-respawn — the substrate respects this honestly rather than pretending it can interrupt mid-generation.

**Trigger divergence is the topology author's responsibility.** A Trigger whose predicate is permanently satisfied by its own firings will fire without bound. The substrate does not detect this; it provides the tools to prevent it (firing policies, keyed deduplication, TerminationPolicy).

## What this enables

**Code synthesis with overlap.** A writer Producer streams; a tree-sitter Producer wired to a View on the writer's buffer emits typed AST events; a typecheck Producer is fired by a Trigger the moment a complete top-level declaration lands; a test-runner Producer is fired once a function is fully written. Writer still streaming, typecheck already running, test-runner already loading. Wall-clock latency drops because nothing is sequential that doesn't have to be.

**Heterogeneous pipelines.** An LLM Producer emits a draft; a sentiment-analyzer Producer (a small classical ML model, not an LLM) reads the draft and emits typed sentiment events; a classifier Producer reads the sentiment events and emits a typed routing decision; a Trigger on the routing decision fires one of several downstream LLM Producers with the original draft and the classification routed in. None of the Producers are the same kind of computation; the substrate doesn't care.

**Ensemble generation.** N cheap weak Producers run the same input with different decoding seeds, all streaming into one Bus; an adjudicator Producer is fired when a Bus-view predicate ("≥3 final-answer events") is satisfied.

**Pair coding.** A Navigator Producer subscribed to a View of the Driver's buffer emits typed suggestion events; a Route stages suggestions for the Driver's next chunked instantiation.

**Code teams.** Writers per module fired by Triggers on task_assigned events from a Planner Producer; reviewer Producer fired by a fan-in Trigger over per-module completion events; revisions retried via PerEvent Triggers with reviewer notes routed into the next writer instantiation.

**Adversarial pairs.** Writer and vulnerability-finder Producers stream concurrently from t=0; finder reads the writer's View and emits typed challenge events; a Trigger with predicate on challenge events fires a refinement Producer.

**Game-theoretic simulation.** Two Producers play iterated prisoner's dilemma. Each reads its View of the opponent's prior moves and emits a typed move event. A payoff-calculator Producer (deterministic) reads both move events and emits a payoff event. A Trigger on payoff events fires the next round of both Producers with the updated history routed in. A TerminationPolicy ends the run after N rounds or on a convergence condition.

**Population simulation.** A population of stochastic agent Producers started at t=0, each emitting typed action events; a world-state Producer subscribed to all actions emits typed world-state events; agents' next-step inputs are routed from world-state updates. The substrate runs the whole simulation as a streaming dataflow; the bus is the simulation log.

**Streaming research synthesis.** M retrievers stream candidates concurrently; a synthesizer Producer fired at the first relevance-predicate cross from any of them; a fact-checker Producer subscribed to the synthesizer's View routes corrections into the synthesizer's next instantiation.

**Recursive decomposition.** A Planner emits N subtask events; one Trigger with PerEvent firing fires N Solver Producers; each Solver may itself emit further subtask events, which the same Trigger matches (it does not check depth), giving arbitrary-depth recursion without per-depth rules.

**Tool-using chains.** Tools are first-class Producers on the Bus, not synchronous subroutines. Tool output streams into the Bus the same way LLM output does; downstream Producers are fired by Triggers on tool-completion or partial-result predicates. An "agent loop" is a chain of (Model Producer → Tool Producer → Model Producer → …) instantiations gated by event-local predicates; each model call is a discrete, independently replayable Producer.

**Conversation.** Two LLM Producers fired by alternating Triggers with chunk-boundary predicates on each other's buffers. The TerminationPolicy interprets a Producer-emitted convergence signal as cancel-all-others + finalise. No special vocabulary; conversation is one topology.

These examples are not exhaustive applications — they are building blocks, and the substrate composes. A code-team topology can include an ensemble within one of its writer slots. A conversation can be wrapped in an adversarial pair. A simulation can include LLMs as some of its agents and deterministic transforms as others. A TerminationPolicy can be built from smaller policies; a heterogeneous pipeline can route into a recursive decomposition. Composition is the substrate's design ideology, not an implementation detail bolted on afterwards.

## Decisions made (with rationale)

**Public API.** The substrate is importable as a library. Any CLI is one consumer.

**Producer identity.** Typed `ProducerId` with kind metadata. Not raw strings, not anonymous UUIDs. The shape is `{kind: str, instance_id: str, parent_id: ProducerId | None, metadata: dict}`. `kind` identifies the Producer kind; `instance_id` is unique within a run; `parent_id` references the Producer whose Trigger created this one (or null at root). `metadata` is an open dict for extensibility. Spawn ancestry is reconstructable from control-plane events (`TriggerFired` records the parent); the ID stays flat rather than embedding a full path.

**Bus total ordering.** Concurrent appends are serialized at the bus. This was a deliberate choice over partial ordering. Partial ordering is more permissive but makes View consistency and predicate evaluation semantics difficult to define without a Naiad-style timestamp system. Total ordering is simpler, replayable without ambiguity, and sufficient for the substrate's goals. The cost is that the bus is a serialization bottleneck; this is the right tradeoff for a system whose throughput is dominated by stochastic Producer latency (LLM calls), not append rate.

**Bus persistence.** Both supported. Per-run is the default; persistent across runs is opt-in for cross-run pattern work.

**Predicate language.** Host-language callables. A composable predicate algebra may emerge later if common patterns crystallise; it is not a substrate requirement. The predicate budget (O(1) or near-O(1)) is enforced by the runtime.

**Input immutability.** A formal contract on Producer, not a recommendation. Running Producers cannot receive injected messages mid-stream. This was the cleanest solution to the "live context" problem: rather than inventing a mid-stream injection protocol (with all its ordering and consistency problems), the substrate makes instantiation boundaries the unit of input change. Routes operate exclusively at these boundaries.

**Route push vs. pull.** Both. Push is default. Pull is available from the `input_builder` for lazy resolution.

**Route timing.** Staged messages become visible at the next Trigger firing after the route-triggering event's append cycle. This is the most consistent option given total ordering: it means `input_builder` sees a fully settled bus state when it runs.

**Cancellation propagation.** Flat by default; subtree cancellation is an opt-in named composition. The default prevents surprising cascade cancellations in fan-out topologies.

**TerminationPolicy form.** Arbitrary host-language callbacks. A closed enum of named recipes ships on top as a convenience. Per-run policies override per-Producer policies at run scope; composition is explicit.

**Topology patterns (retry, progress gating).** Named as patterns, not promoted to primitives. Retry is a Trigger on `ProducerFailed`; progress gating is a Bus-view predicate. Both are fully expressible with existing primitives. Promoting them to primitives would either narrow their expressibility or make the primitive set larger without adding capability.

**Trace/replay UI.** Separate tool reading the persisted event log. Not part of the substrate.

**Application terminology in conversation topologies.** Producers stay Producers. Conversation topologies do not get bespoke runtime vocabulary.

**Top-level preset construct.** None. Named topologies (e.g. `watch`, `study`, or any other) are factory functions in the topology registry.

**CLI surface.** `--topology <name>` against a registry of bundled topologies, plus `--topology-module path/to/mod.py` for user-written Python. Per-topology flags are accepted by the topology factory.

**Documentation splitting.** Eventually three artifacts (concept note, runtime primitive spec, current-code migration note). One unified document while the runtime spec hardens.

**Dynamic topology / recursive Triggers.** Arbitrary depth. A Trigger's predicate may match events from any Producer including descendants of its own previous firings. No per-depth Trigger registration is required.

**Producer scope.** Not LLM-specific. Producers may be LLMs, classical ML models, deterministic transforms, subprocesses, simulators, sensors, or anything with a typed-input streaming-event-output shape.

**TerminationPolicy composition.** Policies compose. The substrate ships building-block policies (`cancel-all-others`, `let-finish`, `quiescence-with-watchdog`, `threshold-count`, `all-completed`) that combine via the host language. Per-Producer and per-run policies coexist via the scoping rules described in §The primitives: TerminationPolicy.

**Route aggregation.** Routes are one-event-in / one-message-out. Aggregation is a Producer pattern: a Producer subscribes to a stream of events and emits a single aggregated event, which a normal Route then consumes. This keeps the routing primitive lean.

**Event encoding for the persistent-bus opt-in.** JSONL (one JSON object per event) is the default encoder. Simple, debuggable, universal, streamable. The encoder is pluggable for callers who need binary formats (msgpack, protobuf), columnar stores, or integration with an external event-store technology.

**Event identity.** Events are identified by bus sequence number, not wall-clock timestamp. Sequence numbers are stable across replay; wall-clock timestamps are not. Predicates and Views use sequence numbers for all ordering decisions.

## Implementation-time choices

Not substrate design questions — choices to make at implementation time by picking the best standard option for the job. Naming them so they aren't confused with open design questions:

**Concurrency model.** Pick the most appropriate runtime (asyncio, structured concurrency, alternatives). The substrate doesn't constrain this; the implementation chooses.

**Bus serialization mechanism.** The bus is a total order; the implementation must serialize concurrent appends. A single-writer queue with async handoff is the simplest correct option. The implementation should not invent novel serialization mechanisms.

**Backpressure mechanism on the bus.** Use a standard, well-understood approach (bounded queues, credit-based per the Reactive Streams specification) after surveying common practice. Don't invent. LLM Producer throughput is the dominant bottleneck; bus backpressure is primarily a concern for deterministic Producers (parsers, simulators) that can outrun the bus.

**Predicate budget enforcement.** Timeout or instruction-count limit on predicate evaluation. The implementation picks the mechanism; the contract (O(1) or near-O(1)) is a substrate requirement.
